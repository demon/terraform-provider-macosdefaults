# Development

How the provider is put together, and the few decisions that shape everything else. For setup and
testing, see [CONTRIBUTING.md](CONTRIBUTING.md).

## The big picture

There's no remote API. The provider runs `/usr/bin/defaults` on the Mac running Terraform, as
whoever runs Terraform. So:

- It only works on macOS, but it compiles everywhere so unit tests and lint run on Linux CI.
- State describes one machine. Applying the same config on another Mac manages a different set of
  real objects.
- The interesting failures are missing keys, Full Disk Access denials, type mismatches, and
  `cfprefsd` caching, not network errors.

It's built on the Terraform Plugin Framework (not SDKv2).

## Layout

```
main.go                  provider server entrypoint
internal/defaults/       wrapper around /usr/bin/defaults (the only place that runs processes)
internal/plistvalue/     HCL <-> plist value conversion and comparison
internal/provider/       provider, resources, data sources
internal/providerutil/   shared Configure plumbing, validators, plan modifiers
internal/acctest/        acceptance-test helpers
examples/                Terraform examples, inlined into docs/
docs/                    generated by `make generate`, don't edit by hand
```

## Design decisions

**Only `internal/defaults` touches the system.** It runs `/usr/bin/defaults` by absolute path with
an argument list, never through a shell. Everything else talks to a `Runner` interface, which is
why the unit tests can swap in an in-memory fake.

**Reads use `defaults export`, writes use XML fragments.** `defaults read` output is ambiguous
(`true` and `1` look the same), so the provider exports the domain as XML and parses it. Writes
pass every value as a plist fragment (`'<real>48</real>'`), which preserves the type exactly and
can't be mistaken for a flag.

**Never touch the plist files directly.** `cfprefsd` caches preferences, and editing the files
behind its back loses writes.

**Only manage what the config names.** Deleting a resource deletes one key, never a domain.

**Comparison is type-aware.** `internal/plistvalue` decides whether state matches the machine.
A boolean stored as integer 0/1 counts as equal (apps do that a lot); any other type change is
drift.

**Scopes and root.** `user` and `current_host` need a normal user; `system` writes
`/Library/Preferences` and needs root. The provider never elevates itself, and a mismatch is a
plan-time error, because running a user-scope config as root would quietly change root's
preferences instead of yours.

**One spelling per domain.** `-g`, `.GlobalPreferences`, and plist paths are rejected in favour of `NSGlobalDomain` and plain domain names, so the same setting can't show up twice in state.
